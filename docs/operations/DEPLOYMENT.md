## PR-B.2 mixed-mode receiver pipeline — operational notes

PR-B.2 enables an additive `pg_notify('agent_inbox')` fanout from the receiver pipeline
for the bots listed in `RECEIVER_PIPELINE_BOTS` (default: `auditor`). The existing
per-bot Discord client + `message_queue` delivery paths keep running unchanged, so
mixed-mode is purely additive: any bot in the canary set receives messages via BOTH
the queue path AND the new `LISTEN agent_inbox` path. Subscribers' in-process
`processedIds` Set handles double-delivery.

> 注: 当初 PR-B.2 description は `pushToChannelServer` 経由を前提にしていたが、Phase 4 (Issue #130) で同 path は廃止、PR #193 で channel-server.ts 自体も削除済。現在の per-bot 経路は message_queue + outbound_queue。

### Connection-pool monitoring (CTO scope #7, Spike 2 finding)

PostgreSQL `max_connections` defaults to **100**. During mixed mode the daemon holds
two cohorts of connections:

| cohort | connection count | notes |
|---|---|---|
| Per-bot Discord client + listener | 1-2 per bot | scaled to N = `EXPECTED_BOTS.length` |
| Send/save tool pool (`pg.Pool`) | up to `max` | currently 10 (default), can spike under load |
| Spike 2 PoC stress harness | up to 20 | only used during PoC; not in steady state |

Watch for `error: sorry, too many clients already` (PostgreSQL code `53300`) in the
daemon stderr — this is the symptom of hitting `max_connections`. If it appears:

1. `psql -d agent_comms -c "SELECT count(*) FROM pg_stat_activity WHERE datname = 'agent_comms';"`
2. If `> 80`, raise `max_connections` in `postgresql.conf` (typical bump to 200) and
   `pg_ctl reload`. Restart not required.
3. If only one cohort is bloated, lower its pool max in code rather than expanding the
   global ceiling.

### Dedup-safe `saveMessage` (Spike 2 finding)

`saveMessage` now uses `INSERT ... ON CONFLICT (discord_message_id) WHERE
discord_message_id IS NOT NULL DO NOTHING RETURNING id` for inbound rows that have
a `discord_message_id` in metadata. The predicate is **repeated on the ON CONFLICT
clause** so the planner matches the partial unique index `uq_agent_messages_discord_id`
(otherwise PostgreSQL rejects with code `42P10`). On race loss, a `SELECT` fallback
returns the existing row's id so the caller's downstream work (metadata.to UPDATE,
push) targets the same row. See `tests/pr-b-2-mixed-mode.test.ts` for coverage.

### Migration backfill divergence from spec §C1

Spec §C1 recommends backfilling `discord_message_id` from `metadata->>'discord_message_id'`
for all existing inbound rows. agent-comms-mcp does **NOT** do this because the legacy
per-bot architecture inserted one row PER BOT for each Discord message — production
data has 22-23 duplicates per Discord message ID, which would block the partial unique
index creation. Legacy rows keep `discord_message_id = NULL`; the partial unique index
only enforces uniqueness for non-NULL values, so legacy rows are unconstrained. New
inbound writes via `saveMessage` populate the column going forward. The metadata copy
stays intact for backwards-compat reads.
