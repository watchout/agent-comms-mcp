# AUN Agent Turn Ledger Contract

> Status: proposed
> Slice: CP-50A agent turn ledger
> Last updated: 2026-06-01

## Purpose

AUN must record durable turn evidence before a runtime sees claimed work.

CP-40 gives the system a deterministic receive path and runtime adapter
boundary. CP-50A defines the ledger that makes runtime invocation observable,
leased, timeout-bound, and recoverable. The ledger is the control-plane proof
that one active baton is being processed by one responsible runtime turn.

Without this ledger, `received` and `in_progress` rows can be visible in the
queue but the system cannot distinguish a live runtime, a crashed adapter, a
stale prompt, or a duplicated invocation.

## Terms

| Term | Meaning |
|---|---|
| agent turn | One bounded runtime attempt to process one claimed queue row for one active baton. |
| turn ledger | Durable table or equivalent records that describe agent turn lifecycle. |
| turn lease | Fenced lease proving that only one runner owns the current turn. |
| runtime invocation | Adapter call that starts Codex, Claude Code, OpenClaw, or another runtime. |
| heartbeat | Durable "still alive" update from the runner or adapter while the turn is active. |
| stale turn | A turn whose lease/heartbeat exceeded policy and can be recovered. |

`worker_activity` may remain an operator visibility table. It is not a
substitute for the turn ledger unless the implementation explicitly adds every
required field and invariant below.

## Product Invariants

1. Runtime invocation must not start until a turn ledger row exists.
2. A turn ledger row must reference exactly one `queue_id`.
3. A turn ledger row must reference the active conversation/baton when those
   identifiers are available.
4. One queue row may have at most one active turn at a time.
5. One active baton may have at most one active turn at a time.
6. The runtime adapter receives the turn id and fencing evidence.
7. Heartbeats update the turn, not only process-local memory.
8. Recovery code must use turn lease and heartbeat evidence before retrying.
9. A stale turn must be made inactive before a new turn starts.
10. LLM output cannot directly mark the turn recovered, abandoned, or closed;
    deterministic runner code must do that.

## Required Data Shape

Implementation may add a dedicated table or extend an existing table, but it
must represent these fields:

```ts
type AgentTurnLedgerRow = {
  turn_id: string
  queue_id: string
  message_id: string
  agent_id: string
  runtime_kind: 'codex' | 'claude' | 'openclaw' | 'other'
  runtime_instance_id: string | null
  conversation_id: string | null
  baton_id: string | null
  claim_lease_id: string
  claim_fencing_token: number | string
  status: 'starting' | 'running' | 'completed' | 'failed' | 'quarantined' | 'stale_reclaimed'
  started_at: string
  heartbeat_at: string | null
  deadline_at: string
  completed_at: string | null
  result_ref: string | null
  failure_code: string | null
  failure_detail: string | null
}
```

Rules:

- `turn_id` is generated by deterministic runner code before adapter launch.
- `queue_id`, `message_id`, and `agent_id` must match the claimed queue row.
- `conversation_id` and `baton_id` are nullable only while earlier slices have
  not populated them.
- `claim_lease_id` and `claim_fencing_token` must fail closed if missing.
- active statuses are `starting` and `running`; terminal statuses are
  `completed`, `failed`, `quarantined`, and `stale_reclaimed`.
- `deadline_at` is required. Open-ended runtime turns are forbidden.

## State Transitions

Allowed turn transitions:

```text
starting -> running
starting -> failed
starting -> stale_reclaimed
running  -> completed
running  -> failed
running  -> quarantined
running  -> stale_reclaimed
```

Forbidden transitions:

- terminal -> active
- active -> active for a different `turn_id` on the same queue row
- active -> active for a different `turn_id` on the same baton
- any transition requested only by runtime prose

The queue transition `received -> in_progress` must occur after the turn ledger
row is created and before the runtime sees the message body. The same
transaction or fenced operation must make it impossible for another runner to
start a second turn for the same work.

## Runner Contract

Before invoking a runtime adapter, the process runner must:

1. verify the queue row is claimed by the expected `agent_id`
2. verify no active turn exists for the same `queue_id`
3. verify no active turn exists for the same active `baton_id`, when present
4. acquire or verify a turn lease with fencing token
5. create the turn ledger row in `starting`
6. move the queue row to `in_progress`
7. pass `turn_id`, lease id, fencing token, queue context, and baton context to
   the runtime adapter

During runtime execution, the runner or adapter must heartbeat the turn before
`heartbeat_at` becomes stale.

After runtime execution, the completion runner must close the turn with a typed
result reference before applying reply/no-reply/handoff/retry/quarantine.

## Recovery Contract

Recovery logic must evaluate both queue state and turn ledger state.

Required recovery checks:

- queue status
- active turn status
- turn lease validity
- heartbeat freshness
- runtime instance liveness, when available
- baton ownership
- deadline expiration

If a turn is stale, recovery must first transition the existing turn to
`stale_reclaimed` or `quarantined` with audit evidence. Only then may it create
a new turn for the same queue row or baton.

## Failure Codes

| Code | Meaning |
|---|---|
| `TURN_LEDGER_REQUIRED` | Runtime invocation was requested without durable turn row. |
| `TURN_ALREADY_ACTIVE` | Queue row or baton already has an active turn. |
| `TURN_LEASE_REQUIRED` | Missing or invalid lease/fencing token. |
| `TURN_HEARTBEAT_STALE` | Heartbeat exceeded policy and requires recovery. |
| `TURN_DEADLINE_EXCEEDED` | Turn passed `deadline_at`. |
| `TURN_BATON_MISMATCH` | Turn baton does not match current active baton. |
| `TURN_QUEUE_MISMATCH` | Turn queue/message/agent tuple does not match claimed row. |
| `TURN_RUNTIME_MISMATCH` | Runtime identity does not match the turn ledger row. |

## Audit Evidence

Every turn lifecycle transition must write audit evidence with:

- `turn_id`
- `queue_id`
- `message_id`
- `agent_id`
- `runtime_kind`
- `runtime_instance_id` or null
- `conversation_id` and `baton_id` or null
- previous and next turn status
- lease id and fencing token
- heartbeat/deadline timestamps
- failure code/detail when present

The completion runner must link its typed runtime result to the turn ledger via
`result_ref` or an equivalent durable result id.

## Tests Required For Implementation

Implementation PRs must include focused coverage for:

1. process runner creates a turn row before invoking the runtime adapter.
2. queue row transitions `received -> in_progress` only after turn creation.
3. duplicate active turn for the same `queue_id` fails with
   `TURN_ALREADY_ACTIVE`.
4. duplicate active turn for the same `baton_id` fails with
   `TURN_ALREADY_ACTIVE`.
5. missing lease/fencing token fails with `TURN_LEASE_REQUIRED`.
6. runtime adapter input contains `turn_id` and fencing evidence.
7. heartbeat updates the durable turn row.
8. stale heartbeat is recoverable only after the prior turn is marked
   `stale_reclaimed` or `quarantined`.
9. completion result links back to `turn_id`.
10. recovery cannot create a second active baton or second active turn.

## Non-Goals

- This contract does not define reply/no-reply/handoff outcome semantics; CP-50B
  and CP-60 own those.
- This contract does not require replacing `worker_activity`.
- This contract does not restart runtimes or state_daemon.
- This contract does not decide the final schema migration shape.

## Acceptance Criteria

CP-50A is complete when:

- every runtime invocation has a durable turn row before launch
- active turn uniqueness is enforced for queue row and baton
- lease, heartbeat, deadline, and result evidence are durable
- stale turns can be recovered without duplicate active work
- runtime adapters cannot bypass the turn ledger
