## Critical 修正への現コード突き合わせ

### C1 (discord_message_id 列追加) — ✅ 賛同 / **必須追記**

方針賛同。**ただしマイグレーション仕様に backfill が抜けている**。

- **現状**: 既存 inbound 行は `metadata->>'discord_message_id'` に Discord native ID が入っている (今日の事故デバッグ中に大量に確認済み)
- **必要**: ALTER TABLE 直後に
  ```sql
  UPDATE agent_messages
     SET discord_message_id = metadata->>'discord_message_id'
   WHERE direction = 'inbound'
     AND metadata ? 'discord_message_id'
  ```
  を migration に含める
- **理由**: backfill が無いと PG partial unique index は機能するが、reply chain 解決時に旧データが NULL → fallback 経路を毎回踏む。SQLite モードでは「receiver は必ず埋める」前提が成立しなくなる (旧データが NULL のままなので)
- **要望**: spec §C1「修正方針」に backfill 1 行追記

### C2 (routeMessage 統一) — ✅ 賛同 / spec の前提記述を訂正したい

方針賛同。**ただし v0.1.0 doc の前提が現コードと食い違っている点を spec で更新したい**。

- v0.1.0 doc の主張: 「§8.2 sendツールは routeInbound を経由しない」
- **現コード (`server.ts:2040`, `server.ts:2149`)**: send tool は **既に** `dest.members.includes(agentId)` で NOT_A_MEMBER をチェックしており、**既に** `routeInbound(...)` を呼んで delivery filter を適用している
- C2 のリファクタ自体 (routeInbound → routeMessage + sourceType) は正しい (2 経路の重複ロジックを 1 関数に集約) が、「完全にスキップされる」という記述は誤解を生むので、**「現状は 2 経路で重複実装、リファクタで 1 関数に統合」と訂正**してほしい
- 影響: spec §C2 の「問題」セクションのみ。実装方針はそのまま OK

### C3 (reply_to 緩和 + Mode B) — ⚠️ PR#89 との連続性を spec で説明してほしい

- 今日の朝 (commit `d61a86d`) で「reply_to 必須、last_received_context 廃止」を SSOT §4.2 に明記してマージ済み。v0.2.0 で Mode B を追加すると **同日中に自分の決定を覆す形** になる
- Mode B の「explicit channel_id 指定」が `last_received_context`（暗黙状態）と何が本質的に違うのかを spec に書いてほしい。私の理解では:
  - explicit > implicit
  - bot が明示的に渡すので非決定論性が無い
  - cron / proactive のユースケースをカバーするため必要
- これを spec に 2-3 行明記すれば PR#89 との不整合の説明になる
- **位置づけ**: ADR-041 起草時に PR#89 を「Mode A の実装」、ADR-041 を「Mode A + Mode B」として位置づけて、PR#89 の決定を Superseded ではなく **「拡張」** として連続性を出すのが綺麗
- agent-comms-cli `notify` コマンドは Mode B のラッパとして実装する旨、§C3 影響範囲に入っている ✅

### C4 (overflow 受信側) — ⚠️ **必須: 設計方針を明示選択**

**現実装は overflow を必要としていない設計なので、spec で明示的に方針選択してほしい**。

- 現コード `server.ts:2132` の `pg_notify` payload は `{event, to, message_id, channel_id}` のみ (約 100 byte)。**content は payload に入れない**。subscribe 側は ID を受け取って DB から SELECT する **pull-on-notify モデル**
- v0.2.0 receiver+MessageBus 設計では payload に content を入れる前提に見える (§5 の `bus.publish('outbound', {...content...})`)。これは Postgres NOTIFY の 8000 byte 制限に簡単に当たる

**選択肢**:

| 案 | 内容 | 実装複雑度 | DB クエリ | 8KB 制約 |
|----|------|-----------|----------|---------|
| α | pg_notify は ID のみ、bot は ID で SELECT (現方式踏襲) | 低 | +1 / msg | 不要 |
| β | payload-in-notify + overflow テーブル (§C4 通り) | 高 | -1 / msg | 必要 |

**私の推奨: α**。理由:

1. 現実装の実績がある (今日の事故でも pg_notify 経路は健全だった)
2. overflow logic の試験面積削減
3. Postgres NOTIFY 8KB 制限はハード制約。境界が静かに壊れるバグが怖い
4. DB クエリ +1/msg のコストは現状の負荷で誤差レベル

**要望**: spec で α / β どちらかを **明示的に決め打ち**

### C5 (専用 receiver bot) — ✅ 賛同 / トークン分離方針を明文化

**1 点明示してほしい**: receive と send のトークン分離方針。

```
receive: 1 個の `agent-com-receiver` bot token (Gateway intents フル)
send:    N 個の per-agent bot token (REST POST、Gateway 不使用)
```

これにより「Discord 上では各 bot が自分の名前で発言、受信は 1 体に集約」という二重視点を実現。proposal §7.2 の `db.getAgentDiscordToken(agent_id)` で示唆されているが、§7.3 で明文化してほしい。

## High 修正への現コード突き合わせ

### H1 (catch-up) — ✅ 賛同 / 3 点追加要望

1. **初回起動時の cold-start 動作**: `lastSeenDiscordId` が NULL の場合 `messages.fetch({after: undefined, limit: 100})` は最新 100 件を返す。全 channel × 100 件の re-fetch が走る。`ON CONFLICT DO NOTHING` で重複は弾けるが noise が大きい。**初回起動時は `lastSeenDiscordId = 現在時刻 snowflake` で skip** する初期化ロジックを spec に追記したい
2. **catch-up 並列度の上限**: 16 channel × 1000 件で REST burst 16,000 req。@discordjs/rest の rate limit 自動制御に任せると順次完走で 5-10 分。spec で「catch-up 中は health check が degraded を返す」を明記
3. **operator alert の宛先 channel**: §H1 修正後コード `notifyOperator(alertMsg)` の実装場所が未定義。`#alerts` channel に投稿するなら channel_adapters に登録要

### H2 (mixed モード dedup) — ⚠️ **必須: no-op INSERT のハンドリング仕様**

**mixed 期間中の routing が壊れる懸念**。

- 現在の daemon は per-bot Discord client が **独立に** onMessage を受け取り、**独立に** DB INSERT する (ARC が指摘した「5 重 INSERT」の正体)。受信した bot の routeInbound 結果でその bot のみに配信される
- mixed モード期間中、receiver と旧 daemon が同じ Discord メッセージで競合 INSERT する。`ON CONFLICT DO NOTHING` で 1 行に確定するが、**敗者側の `handleInboundMessage` は INSERT を no-op として正しくハンドルする必要がある**
- 現コード `handleInboundMessage` (`server.ts:1370`) は INSERT 結果の `messageId` を信じて `metadata.to` UPDATE と push を実行する。`ON CONFLICT DO NOTHING` 時は `INSERT ... RETURNING id` が空を返すので `messageId` が undefined になる → **push が機能しない**

**要望**: 「INSERT が no-op だった場合、既存行の id を SELECT して downstream を続行」ロジックを spec で明示。実装もここを refactor 対象として記録。

これが無いと Phase A デプロイ直後に「receiver と daemon の race で push が落ちる」事故が起きる可能性高い。

### H3 (`@discordjs/rest`) — ✅ そのまま OK

既に discord.js の transitive dep なので追加なし。

### H4 (TTL cache) — ✅ 賛同 / cache invalidation の発火元

**1 点追加**: cache invalidation の発火元。

- proposal は `bus.subscribe('channels_updated', ...)` で invalidate するが、channels の mutation は **CLI** (`cli/index.ts` の `channel add-member` 等) と **bot 間 send** (DM auto-create) から発生
- どちらも `pg_notify('channels_updated', '')` を発火する責務を負う必要がある。現 CLI コードは未対応
- spec §H4 に「mutation 元（CLI / bot send tool / migration）は全て pg_notify を発火する」を追記

## 追加で気になる点

### A2 (動的 re-subscribe Phase 2 punt) — ⚠️ 現運用との衝突

- 現在 16 bot 構成。channel メンバー追加のたびに **全 bot 再起動はオペレーション負荷が大きい**
- Phase 2 punt は理解するが、Phase 1 の暫定運用として「該当 bot 1 体だけ再起動できる CLI」を必須にしてほしい (`agent-com restart-bot <id>`)
- 現状の `mcp__agent-comms__restart_bot` ツールは tmux session 名指定で動くので転用可能。spec §A2 の Phase 1 補足として記載

### Q1 PoC spike — ⚠️ **必須: NG だった場合のフォールバック計画**

- Claude Code の MCP client が server からの `notifications/message` をどう扱うか — 仕様上は支援されているが、モデルコンテキストへの注入が confirmed か未検証
- spike で No だった場合の retreat path:
  - **(a)** pull-on-notify (現方式) を v0.2.0 でも維持。push の即時性は失われるが構造改善は成立
  - **(b)** v0.2.0 採用見送り、別アーキテクチャ
- **(a) を デフォルトの retreat path として spec §Q1 に書けば**、spike 結果が NG でも「v0.2.0 採用見送り」ではなく「(a) で進める」が選択肢になる。pull-on-notify は実績あるので失うものは少ない

### operator runbook の不在

A1 で receiver crash 時のリカバリは catch-up 依存と書かれているが、**「receiver が無反応のときに何をすればいいか」のオペレーション手順書** が無い。spec の付録に最小 runbook を追加してほしい:

1. health check endpoint で degraded が出続ける条件
2. 手動再起動コマンド
3. Discord REST 直叩き fallback 手順 (今日 CTO がやったやつ)

## 実装担当からの確認質問 (PoC 着手前に明確化したい)

- **Q-Dev-1**: receiver の物理位置。`bin/agent-com-receiver` 新規? `server.ts` の `TRANSPORT_MODE='receiver'` 追加? 後者だと現 daemon コードと共存しやすい
- **Q-Dev-2**: `core/route-message.ts` を `server.ts` から切り出す前提か? 現 server.ts は monolithic (3000 行超)。リファクタの順序として「先に core/ 切り出し → 後で receiver 追加」が安全。PoC スコープに含めるか別 PR か
- **Q-Dev-3**: PoC 最小スコープの定義。私の理解: 1 receiver process + 1 bot MCP server (subscribe あり) + 1 channel + 1 inbound + 1 outbound round-trip + Q1 検証。これで合っているか
- **Q-Dev-4**: PoC 期間中の 16 bot 運用。PoC bot 1 体だけ新方式に切り替えた状態で残り 15 bot は旧方式。その間 receiver の DB INSERT と旧 daemon の DB INSERT が併存する (まさに mixed モード)。**PoC = mixed モード dedup の実証も兼ねる** という理解で良いか
